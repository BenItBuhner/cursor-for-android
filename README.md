# cursor-for-android

An unofficial, native Android client for [Cursor Cloud Agents](https://cursor.com/docs/cloud-agent/api/endpoints), built with Kotlin and Jetpack Compose. It reproduces the official Cursor Agents application (the desktop Agents window and cursor.com/agents) with Android primitives: the same sidebar, the composer-first New Chat pane with the recent-chats list, the conversation view, and the design tokens shipped in the desktop build.

Not affiliated with Anysphere, Inc.

## Features

- Sign in with your Cursor account, the way Cursor's own CLI and SDK do: "Continue with Cursor" opens cursor.com in a Custom Tab with a PKCE challenge, the app polls `api2.cursor.sh/auth/poll` for the approval, then spends the released session once on `DashboardService/CreateUserApiKey` to mint a 90-day user API key named after the device (it shows up on cursor.com/dashboard/api like any other key, and can be revoked there). The app comes back on top of the browser as soon as the approval lands. Or paste a user / service-account API key under "Use an API key instead", for teams that restrict user keys. Either way the key is validated against `GET /v1/me`, stored encrypted with the Android Keystore and excluded from backups; the session tokens are never kept. The encrypted store is the only place it is ever written: a Keystore that cannot be used (a master key invalidated by an OS upgrade or a lock-screen change, a device restore) makes the app recreate the store and ask you to sign in again, and a device where it cannot be recreated keeps the key in memory for that session only rather than in the clear — Settings and the sign-in screen say which. Settings shows how you signed in and when a minted key lapses; a lapsed one signs out to a one-tap re-login. The sidebar footer and Settings show the account's actual profile picture (`GET /v1/me` has no field for it, so it comes from the account service's `DashboardService/GetMe` behind the key check, kept with the cached account and falling back to the initials).
- New Chat pane as home: repository / branch / environment selectors, the composer (the "+" menu, model picker with plan mode and auto-PR, send), then the recent chats with preview cards. The branch picker offers the repository's default branch and every branch its agents have started from or pushed — the API has no branch listing, so that is what the app can know — and takes any other branch by name. The model picker lists each model from `GET /v1/models` once; a model's parameters — effort, speed, context window — unfold under it as pickers (a toggle for an on/off parameter, a row of choices otherwise), and every choice resolves to a variant the API lists, so the request never carries a `model.params` combination the model does not accept. Sending opens the chat at once: the prompt (with its images) is on screen and the chat reads "Starting…" before `POST /v1/agents` has answered, with the new row already in the list; the reply swaps in the run and starts its stream. The composer is empty from that moment: the launch belongs to the app, not to the pane that sent it, so going back — or starting another chat — while the server has yet to answer meets a New Chat pane that is ready, never one still occupied by the previous send. The prompt is kept on the device until the legacy transcript has caught up with it, so it never blinks out while `/v0/agents/{id}/conversation` lags behind the run list. A launch that fails, or is stopped from the chat, hands its draft back to the composer (with the reason, for a failure) — as soon as the composer is free, if another draft is being written by then; the app mints the agent id itself (`agentId`), so re-sending an unchanged draft adopts the agent a lost reply may already have created (`409 agent_id_conflict`) instead of launching a duplicate.
- Slash commands, as on cursor.com/agents: typing `/` in either composer opens a popover under the cursor listing what the message can lead with — `/goal` and the other commands, the built-in cloud skills (`/autopilot`, `/review`, `/review-bugbot`, `/review-security`, `/split-to-prs`, `/subscribe`, `/loop`, …), and the repository's own `.cursor/skills`, plugin and synced skills — narrowed by what follows the slash (names first, then descriptions, so `/go` offers `/goal` and a skill whose description mentions Google), and a tap completes the token. The list is the account's, read over the same Connect-JSON channel as the pins from `aiserver.v1.DashboardService`: `GetRepoSlashCommands` for a new chat (the repository at its branch, project plugin skills included), `GetBackgroundComposerSlashCommands` for a follow-up (which also carries the `.cursor/commands` the agent's machine reported, and says when that inventory is still on its way, in which case the popover says so and asks again shortly), and `GetGlobalCommands` for the commands that apply everywhere. Catalogs are cached per repository / agent on disk and revalidated every ten minutes; the built-ins stand in offline, in demo mode and under a key the account service refuses. A name the catalog does not list is still offered and remembered once used, since project and synced skills are real on the VM whether or not anything reported them.
- The composer's "+" menu, as on cursor.com/agents: Multitask (toggles `/multitask` at the front of the prompt), Files (image attachments via the system photo picker), Skills (the same catalog as the `/` popover, searchable, toggled as `/name`), and MCP Servers (HTTP or stdio servers defined in the app, stored encrypted, toggled per server and sent inline as `mcpServers[]` with every prompt while enabled). The same menu sits on the follow-up composer.
- Sidebar (edge-swipe drawer on phones, permanent 280dp column on tablets and foldables): one header row with the "+" new-chat button, search, the filter menu (group by, sort, Repo / Status / Git / Source / Environment filters — the Git filter shows or hides chats by where their pull request stands, open, draft, merged or closed, or that have none; the Source filter is the one cursor.com/agents and the desktop Agents window have, where each chat was started: Cursor desktop, Cursor web, the mobile app, the CLI, Slack, Microsoft Teams, Linear, Jira, source control (GitHub / GitLab / Bitbucket / Origin comments), the API, the SDK, Automations, Bugbot, Grok Bot, plus "This device" for the chats launched from this app and "Other" for Cursor's internals; the Environment filter is where each chat runs, Cursor's cloud, a team pool or one of your machines — and metadata toggles) and the sidebar toggle, then the Projects, Pinned and date groups; pull-to-refresh, long-press actions (pin, rename, open on cursor.com, copy link, archive / unarchive). Rename and archive go through the same account RPCs the desktop Agents window and the iOS app use, so a title or archive changed here shows there and the other way around.
- Cursor Projects, as the Agents Window tells them apart: a Project — the coordinator chat that plans a body of work, delegates it to worker agents and keeps the shared context — leads the sidebar in a Projects group with its icon in its colour (the ten tones and the icon names of the desktop's project appearance picker, `lightning` in the secondary icon tone when none is set), whether or not it is pinned. The chats that hang off a chat — the workers a Project created or adopted, side chats branched off it, cloud subagents it spawned — sit under it as a tree, closed until the count at the row's trailing edge is tapped (the working glyph sits beside the count while a hidden one is running); a child whose parent is not listed, or that is pinned, stands on its own. The public API has no notion of any of this: it is read from the account's list (`projectMetadata`, `managerAgentId`, `sideChatInfo`, `cloudSubagentParent`, derived exactly as the desktop derives `isProject` and its parent links — a record with `projectMetadata` and no manager is a Project, the parent is the first of subagent parent, side-chat parent and manager) and kept on the row across refreshes and on disk like the source.
- Pinned chats are the account's, shared with the desktop Agents window and the iOS app: the pin list is read from `aiserver.v1.BackgroundComposerService/ListBackgroundComposers` (`includePinnedState` → `pinnedBcIds`) after every list refresh and changed with `Pin` / `UnpinBackgroundComposers`, over the same Connect-JSON channel the sign-in uses. Those RPCs take the account session rather than the API key, so the stored key is exchanged for one on demand (`POST api2.cursor.sh/auth/exchange_user_api_key`, the Cursor CLI's `--api-key` login) and the session is kept in memory only. A pin toggled here shows at once and reaches the server now or at the next sync (pending changes survive restarts and win over the server's answer until acknowledged); the first sync of an account pushes the pins made on this device before syncing existed; pinned agents past the list window are fetched by id and kept through later listings. Settings › Chats turns the sync off to keep pins on the device, and shows why it is not going through when it isn't (a device policy, a key the account service refuses).
- Conversation view: transcript (`/v0/agents/{id}/conversation`), run footers ("Worked 3m 5s"), a pull-request button in the header beside the menu once the agent has opened one (the chat's only link to its PR, so a long transcript never scrolls it out of reach), live SSE streaming of the active run and markdown rendering; follow-ups with image attachments (`prompt.images`), stop, and press-and-hold on any prompt or reply to copy it. The turns Cursor starts on its own — a goal carrying over to the next turn, a background subagent reporting back — reach the transcript as `user_message`s made of the `<system_notification>` markup written for the model, not as anything the user said; they render as one row in the trace's own voice ("Goal continued · In the Verity photoreal engine…", "Subagent completed · Contacts, clipping and pose naturalness", red for a failed one) that opens onto the objective or the subagent's report, and press-and-hold still copies the notification as injected. A stream that drops — a network change, the agent's machine waking up after a follow-up (`stream_unavailable`), a server-side `upstream_error` — is a connection problem, not the run's: the trace stays put, the working row says "Reconnecting…", and the stream is resumed with `Last-Event-ID` and backoff for as long as the run record says the run is going; a run whose stream is gone for good is settled from the record instead. Everything the agent does between two replies — its reasoning and tool calls, in the order they happened — is laid out the way Cursor's own client lays out a step group (ported from the desktop build's `tool-action-labels` / `step-group-display`): a thought before any tool call is its own "Thought 3s" row, and the tool calls with the thoughts between them sit behind one summary — "Explored 3 files, 2 searches, ran 1 command", "Edited 2 files, explored 3 files +12 -3", "Ran 1 command" — whose verb shimmers while the work is still going, and which opens onto one line per step in Cursor's words: "Read Timeline.kt", "Grepped ModelSheet in ui", "Searched files *.kt in app", "Edited HomeScreen.kt +12 -3", "Ran ./gradlew test", "Searched web …", "Fetched page …", "Completed task Survey the API", "Explored available tools", and "Ran list_pull_requests in Github" for an MCP tool; a failed call reads "Edit attempted", and one or two bare reads stay as lines rather than a group. A tap on a line opens what the call was asked and what came back — the command and its output, the MCP input and result, the full path or query. Finished runs replay their retained event stream, so the same trace is there to dig into after the fact; a trace seen whole — followed live to its `result` (on screen or by the live notification) or replayed — is kept on disk from then on, and a run that ends while the screen is away, or whose stream broke, is replayed from its first event rather than left as the fragment the screen had. Runs whose log expired (`410 stream_expired`) before it was ever seen keep the text-only transcript.
- Switching model mid-chat, as on cursor.com/agents: the follow-up composer's model chip opens the same picker as New Chat and sends the pick as the run's `model` (the SDK's `agent.send({ model })`; the override is sticky, so later follow-ups keep it), with plan mode per run through `mode`. The API never reports an agent's model, so the chip names what this device launched or last switched the chat to and reads "Model" for chats started elsewhere; the picker shows the chat's model checked when the catalog lists it, and a "Current model" row otherwise.
- Media in replies: the `<img>`, `<video>` and `![alt](src)` an agent writes for its screenshots and recordings render inline. `/opt/cursor/artifacts/…` paths are exchanged for presigned URLs through `GET /v1/agents/{id}/artifacts/download` (cached and refreshed before their 15-minute expiry); images are laid out at one source pixel per dp within the message width and open in a zoomable full-screen viewer, videos show a poster frame and play inline with ExoPlayer.
- Live notifications, the Android counterpart of the iOS app's Live Activities: while agents run, an ongoing notification shows the status, title, current step and a Stop action for one agent, or the total count with one condensed line per agent (live detail for up to eight, then "+N more") for several; when an agent finishes, a card with "Finished", `+80 −230 · 3 Files` (or the duration when no tool reported line counts), the final reply, Review and View PR. On Android 16 it is a promoted Live Update (status-bar chip, lock screen). Backed by a `dataSync` foreground service that only runs while something is running; toggle in Settings › Notifications. The service is supervised rather than fired and forgotten: whether it is up is part of the decision to start it, so a start the platform refused is asked for again with backoff, and a service the platform took down while agents kept running — Android 15 ends a `dataSync` service six hours after the app was last in front, and a process can be killed at any time — is brought back whenever the app is in front. While it is gone and the app is not around to restart it, a persisted `JobScheduler` watchdog (armed for as long as the service is up, so it survives a reboot) reads the run records of the agents that were running and posts their "Finished" cards, and keeps checking until none is left; the live notification itself comes back the next time the app is opened.
- Instant start: the agent list, the transcripts you opened (plus the most recent ones, prefetched in the background), the traces of finished runs (as deep as a conversation pages its runs — 400 per chat, and up to 2 MB of them, oldest let go of first) and the model / repository catalogs are kept on disk (`cacheDir`, wiped on sign-out), so the app renders the last known state immediately and revalidates behind it — an open chat also revalidates when the app returns to the foreground, and the list keeps itself current while a list surface is on screen — the recent cards, an open drawer, the permanent sidebar — with the newest page every 30 s, the newest few hundred rows every few minutes, and the whole list on a pull-to-refresh and at most once an hour (only a listing that reaches the end can tell that an old chat was deleted elsewhere); a run of failed polls backs the interval off instead of knocking every half minute through an outage. Refreshes publish each `/v1/agents` page as it arrives and treat the legacy `/v0/agents` enrichment as best effort, a failed or offline refresh never empties what is on screen, and transient errors (`429`, `5xx`, dropped connections) are retried with backoff for idempotent requests. Whether a chat is running is decided by its latest run, never by the v1 `status`: that field is a lifecycle that reads `ACTIVE` for finished agents too, so the legacy list's status fills it in and the runs still in question after a refresh — a turn that just started or ended, a row that claims to be running — are settled against their records. A row's activity time is the server's `updatedAt`; a stamp made on the device (a follow-up sent, a finish watched) only stands until the server confirms it.
- Home-screen widget ("Chats"): the sidebar's rows on the home screen — the same 36dp rows on the same `#181818` surface, the working dot grid (held on one frame, since widgets cannot animate), the blue unread and red error dots, the pull-request glyph in its state's colour or the neutral branch glyph of a read chat that pushed, the machine glyph and the workspace / age metadata the Chats filter menu toggles. Each widget lists one of three things, picked when it is placed and switchable from its title: recent chats (the New Chat pane's list, newest first), running agents (whatever the Status filter says), or the sidebar's Pinned group; the Repo / Git / Source / Environment filters apply as in the sidebar. A row opens its chat, the cube opens the app, "+" opens the New Chat pane. Rendered with Glance from the same repository, filters and pins the app uses — from the disk cache first, revalidated behind it — and re-rendered whenever any of that changes while the app is alive (a run finishing, a pin, a filter, a theme change, a sign-out); "Match system" follows the system theme even while the app is not running. The widget picker shows a live preview on Android 15, the layout preview on Android 12+, and a rendered image before that.
- Settings with Cursor Dark / Cursor Light / system theme, the pinned-chats sync toggle and its status, and the live-notification toggle; demo mode with an in-memory backend so the UI can be explored without an account.
- In-app updates from this repository's GitHub releases: the app checks the release list (a conditional request, so a repeat costs nothing), maps each `vX.Y.Z` tag to the build's versionCode scheme and offers the newest release above the installed one — release candidates too, when "Include pre-releases" is on. With "Automatic updates" (the default) a persisted `JobScheduler` job checks every 12 hours and the app checks again when it comes forward; the APK is downloaded over Wi-Fi, verified against the SHA-256 GitHub published for it and parsed to confirm it is this package, newer, and signed with the installed key, then installed while the app is off screen — without a prompt on Android 12+ once "Install unknown apps" is allowed (the installer is updating itself), through a notification and the system's confirmation otherwise. Settings › Updates has the manual path: check, download with progress, install, retry; the sidebar shows "Update available" above the account footer. See [In-app updates](#in-app-updates).
- Predictive back (Android 14+): the screen being left rounds its corners and slides out of view in the direction of the swipe (right for a left-edge gesture, left for a right-edge one), trailing the finger vertically, while the screen underneath fades in and drifts into place behind it — neither changes size. The sidebar drawer slides back toward its edge in step with the gesture, whichever edge the swipe came from, and keeps its size; bottom sheets shrink with the gesture, the filter sheet's drill-in pages slide back under the finger, and from the New Chat pane the system's back-to-home animation plays. Cancelling a gesture rewinds from wherever it was; releasing commits from there, and a new gesture that starts mid-rewind takes over. Forward navigation plays the same transition backwards.

## Build

Requirements: JDK 17+, Android SDK with platform 36 (compileSdk; targetSdk stays 35) and build-tools 35.

```bash
./gradlew :app:assembleDebug          # APK at app/build/outputs/apk/debug/app-debug.apk
./gradlew :app:testDebugUnitTest      # JVM unit tests
./gradlew :app:recordRoborazziDebug   # re-render screenshots/ from the demo backend
./gradlew :app:verifyRoborazziDebug   # compare the demo walkthrough against screenshots/
./gradlew :app:assembleRelease        # R8-minified APK; signed with the debug key unless release signing is configured
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

## CI and releases

Everything runs on GitHub Actions (`.github/workflows/`); the shared toolchain (JDK 17, SDK 35, Gradle cache) lives in `.github/actions/android-toolchain`.

| Workflow | Runs on | Does |
| --- | --- | --- |
| `ci.yml` | pushes to `main`, pull requests | `lintDebug`, debug + release APKs (downloadable from the run's artifacts, stamped `<app.versionName>-dev.<run>+g<sha>`, e.g. `0.2.0-dev.42+gabc1234`), JVM unit tests, screenshot verification against `screenshots/` |
| `release.yml` | tags `vX.Y.Z`, or manually for an existing tag | lint + tests, then a signed release APK and AAB, the R8 `mapping.txt`, `SHA256SUMS.txt` and a GitHub Release with generated notes (`.github/release.yml` groups them by label) |
| `update-screenshots.yml` | manually | re-records `screenshots/` on a clean runner and opens a pull request |

### Cutting a release

```bash
git tag v0.2.0 && git push origin v0.2.0        # stable release, marked "latest"
git tag v0.2.0-rc.1 && git push origin v0.2.0-rc.1   # pre-release
```

The tag is the only input. `versionName` is the tag without the `v`; `versionCode` is derived from it as `MAJOR * 1_000_000 + MINOR * 10_000 + PATCH * 100 + STAGE`, where `STAGE` is 0–24 for `alpha.N`, 25–49 for `beta.N`, 50–98 for `rc.N` and 99 for a stable version, so every pre-release sorts below its final build (`0.2.0-rc.1` → `20051`, `0.2.0` → `20099`). Local and CI dev builds use `app.versionName` from `gradle.properties`; bump it after tagging so dev builds report the version they lead up to. CI appends `-Papp.versionNameSuffix=-dev.<run>+g<sha>`, and the code is derived from the resolved name, not the base: a `0.2.0-dev.148+gabc1234` build is `20024`, so the `0.2.0` it leads up to is still an update for it. `-Papp.versionName=…` sets the base name; `-Papp.versionCode=…` overrides the derived code. The in-app updater derives the same code from each release tag to decide whether it is newer than the installed build, so the scheme is part of the release contract.

### Release signing

Run `scripts/release-keystore.sh --set-secrets` once (needs a logged-in `gh`). It creates `release.jks` and uploads the `RELEASE_KEYSTORE_BASE64`, `RELEASE_KEYSTORE_PASSWORD`, `RELEASE_KEY_ALIAS` and `RELEASE_KEY_PASSWORD` repository secrets; without `--set-secrets` it prints the values to add by hand. Keep the keystore and password backed up: Android only installs an update if it is signed with the same key, so a key change ends in-app updates for every existing install (the updater notices — the release notes name the certificate — and offers the release page instead of a download that could not be installed). For local release builds, put the same values in a git-ignored `keystore.properties` next to `settings.gradle.kts` (`storeFile`, `storePassword`, `keyAlias`, `keyPassword`).

All four secrets are required to publish. Without them a runner signs with a debug key it generated for itself, which no later run reproduces, so anyone who installed that APK could never be updated in place again — the workflow therefore stops before building rather than publishing one. Debug signing is still what `ci.yml` produces (its release APK only exists to exercise R8) and what a release **dry run** produces, and a dry run never touches the GitHub Release. After signing, `apksigner verify --print-certs` must report a signer, and if the `RELEASE_CERT_SHA256` repository variable (a secret works too) is set it must be that certificate: pin it to the digest the first signed release printed and a wrong or rotated keystore cannot reach users unnoticed.

### In-app updates

The app keeps itself current from the releases the workflow above publishes; nothing else is needed for a release to be picked up. What it relies on:

- The tag is a `vX.Y.Z[-PRERELEASE]` version. Its versionCode is derived exactly as the build does it (`AppVersion.versionCode`), and a release is offered when that code is above the installed `BuildConfig.VERSION_CODE`. Stable tags only, unless the user switches on "Include pre-releases" (a build that is itself a pre-release — an `-rc.N`, or a CI `-dev.N` build — defaults to seeing them). GitHub's pre-release flag counts as well, so a stable tag published as a pre-release stays out of the stable channel until it is promoted. Drafts are ignored.
- The release carries the APK (`cursor-for-android-X.Y.Z.apk`, or any `.apk` asset). The download is verified against GitHub's own SHA-256 digest of the asset, falling back to `SHA256SUMS.txt`; a mismatch is discarded. Before it is offered for installation the file is parsed with `PackageManager`: it must be this package, newer than the installed build, and signed with a certificate the installed build already trusts. Android enforces the same three things at install time; the checks exist so the failure is a sentence in Settings rather than a system error.
- The repository is `app.githubRepo` in `gradle.properties` (`BuildConfig.GITHUB_REPO`); a fork points it at its own releases. Requests are anonymous with a `cursor-for-android/<version>` User-Agent, and conditional (`If-None-Match`), so the periodic check is usually a `304` with no body to transfer or parse. It is not free: GitHub only exempts conditional requests from the rate limit when they are authenticated, so an anonymous `304` still spends one of the 60 requests an hour that IP address gets — enough for the 12-hourly job and the 6-hourly foreground check, but a shared NAT or repeated manual checks can reach it. When it is reached, the reset GitHub reports (`X-RateLimit-Reset`, or `Retry-After` for a secondary limit) is honoured: Settings says when to try again and no request is sent until then.
- The list is read `per_page=100`, and the `Link` header's next page is followed (up to three pages) until a release the channel can install is found, so drafts, source-only tags and a run of pre-releases cannot push the newest eligible stable release out of sight.

How it runs. "Automatic updates" (Settings › Updates, on by default) schedules a persisted `JobScheduler` job — every 12 hours, online, battery not low — and the app also checks when it comes to the foreground, at most every 6 hours. A found release is downloaded only over an unmetered network (the manual "Download" ignores that). A downloaded release is installed the next time the app is off screen and no run is being streamed by the live-notification service, since the install replaces the process. On Android 12+ that happens without a prompt: the session is committed with `USER_ACTION_NOT_REQUIRED`, which the platform honours for an app updating itself once the user has allowed "Install unknown apps" for it (`REQUEST_INSTALL_PACKAGES`; Settings › Updates links to the system page until it is granted) and the app declares `UPDATE_PACKAGES_WITHOUT_USER_ACTION`. On Android 8–11, or before that permission is granted, the update waits behind a "Cursor X.Y.Z is ready to install" notification; tapping it brings up the system's confirmation. The first launch after an update shows "Updated to X.Y.Z" in Settings and cleans up the download. Everything the updater remembers (the last check, the downloaded APK) lives in the cache directory next to, not inside, the account caches, so signing out leaves it alone; the preferences are device-level for the same reason.

Debug builds (`com.cursorforandroid.debug`) check and download like release builds but cannot be updated with a release APK, which is a different package — the post-download check says so. To exercise the updater against an emulator, build a debug APK with `-Papp.updateApiBaseUrl=http://localhost:8080/` (debug builds permit cleartext to `localhost` and `10.0.2.2` for exactly this), serve a release list in GitHub's shape plus the APK of a higher version from the host (`adb reverse tcp:8080 tcp:8080`), and grant the permission with `adb shell appops set com.cursorforandroid.debug REQUEST_INSTALL_PACKAGES allow` to see the silent path. Release builds always talk to `api.github.com`.

### Screenshots

`AppScreenshotTest` pins the clock (`AppClock`) to 2025-01-15 14:00 UTC, the zone and the locale, and disables ripples, so the PNGs render identically on every machine. After an intentional UI change, re-record with `./gradlew :app:recordRoborazziDebug` or the "Update screenshots" workflow and commit `screenshots/`. The demo backend serves its sample artifacts (`app/src/main/assets/demo/`) as `file:///android_asset/` URLs, so `11_conversation_media.png` exercises the real image pipeline without a network; `25`–`27` are the Source and Environment filter pages and the sidebar with the Source filter narrowed to Slack, the CLI and Grok Bot (the demo seeds carry a source each); `03_sidebar.png` leads with the demo's Cursor Project (a coordinator with two workers and a side chat folded under it, `DemoData.composers` standing in for the account's list). `WidgetScreenshotTest` renders the home-screen widget the way a launcher does — the Glance composition to `RemoteViews`, applied under an `AppWidgetHostView` — for `14`–`18_widget_*.png`; `18_widget_preview.png` is also the widget picker's image for launchers before Android 12 (`app/src/main/res/drawable-nodpi/widget_chats_preview.png`), so copy it over when the widget changes.

## API surface used

| Purpose | Endpoint |
| --- | --- |
| Sign in with a Cursor account | `cursor.com/loginDeepControl?challenge&uuid&mode=login&redirectTarget=sdk` (browser), `POST api2.cursor.sh/auth/poll` `{uuid, verifier}` until it stops answering `404` (a backend without that route falls back once to `GET /auth/poll?uuid&verifier`, which puts the verifier in the query string; nothing logs the URLs of this client), then `POST api2.cursor.sh/aiserver.v1.DashboardService/CreateUserApiKey` (Connect protocol, JSON) with the session token — the same handshake `@cursor/sdk`'s `Cursor.auth.login()` performs |
| Account session for the account-level RPCs | `POST api2.cursor.sh/auth/exchange_user_api_key` with the API key as the bearer, body `{}` → `{accessToken, refreshToken}`; re-done when the JWT nears its `exp`, on a `401`, or when the key changes; never written to disk |
| Profile picture (and a name or email `/v1/me` left blank) | `POST api2.cursor.sh/aiserver.v1.DashboardService/GetMe` `{}` → `profilePictureUrl`, `firstName`, `lastName`, `email`, `teamName` (Connect protocol, JSON, session bearer); fetched behind every successful `/v1/me`, best effort, and kept with the cached account |
| Slash commands for the `/` popover and the Skills page | `POST api2.cursor.sh/aiserver.v1.DashboardService/GetRepoSlashCommands` `{repoUrl, gitRef?, includeProjectPluginSkills: true}` for a new chat, `…/GetBackgroundComposerSlashCommands` `{bcId, repoUrl?, gitRef?}` for a follow-up (`skills[]` as `SkillDescriptor`s — name, description, source path, environments — `commands[]` as `CommandDescriptor`s, the older `skillNames[]` / `commandNames[]`, and `machineInventoryPending`), and `…/GetGlobalCommands` `{surface: GLOBAL_COMMAND_SURFACE_GLASS}` (`GlobalCommand`s with `availability` and `disabledSurfaces`; local-only ones are dropped). ## Design tokens and geometry

Taken from the Cursor 3.19 desktop build (`workbench.glass.main.*` and the bundled `theme-cursor` themes): surfaces `#141414` (chat canvas, `--cursor-chrome`), `#181818` (sidebar, inputs, cards); the foreground `#F0F0F0` (light: `#141414`) at 100 / 74 / 60 / 36 % for text, 66 / 52 / 28 % for icons, 20 / 14 / 8 / 6 / 4 % for fills and 20 / 12 / 8 / 4 % for strokes; accents `#81A1C1`, `#3FA266`, `#70B489` (git added), `#FC6B83` (git removed), `#E34671`; radii 4 / 6 / 8 / 12 / 14; type 11 / 12 / 13 / 14 with 14 / 16 / 18 / 22 line heights. UI text uses the system sans (the desktop app uses the platform system font too); code uses the bundled JetBrains Mono (SIL OFL, see `app/licenses`). Icons are line glyphs on a 24-unit grid drawn at a 1.75 stroke, the weight Cursor uses for its 16px icons; their geometry comes from [Lucide](https://lucide.dev) (ISC, see `app/licenses`), while the cube is the official Cursor brand mark (path data verbatim from [cursor.com/brand](https://cursor.com/brand)), the "working" indicator is the web's 3×3 stepping dot grid drawn on a canvas, and the stop square is drawn in-house (`CursorIcons`). Proportions follow the official web app measured at 2x (640px composer with 14px text and 24px round buttons, 6px selection radius, 13px body text with 12px labels, preview cards on the left of recent rows), but everything a finger has to hit is sized for touch rather than a pointer — 44dp header, 32dp icon buttons with 44dp touch targets, 36dp sidebar rows, 44dp list rows — as recorded in `CursorDimens`. The touch layer is separate from the painted box, so controls keep the web's visual size next to their text instead of growing with the finger: the composer's round buttons stay at the web's 24dp beside 14sp input text (touches land over 40dp, and the footer row they sit in is 28dp tall for the model chip), which keeps text and buttons in the web's proportion. See `app/src/main/java/com/cursorforandroid/ui/theme/` for the mapping.

The chosen theme is also handed to the platform (`UiModeManager.setApplicationNightMode`), which is what makes the window drawn behind the first frame — resolved before any of this app's code runs — match it. That API is Android 12 and up; on Android 8 to 11 the launch window follows the system, so a Light theme on a phone in dark mode opens on a dark window for the first frame.

## Navigation

Three destinations (New Chat, Settings, a chat) live on an in-house back stack (`NavStack`, saved across process death) rendered by `CursorNavHost`, which composes at most the resident screen and the one beneath it and drives every transition — pushes, pops and the predictive back gesture — from one seekable progress value. The gesture's `BackEventCompat` is read directly, which is what lets the transition follow the swipe edge and the finger; `navigation-compose` cannot expose either to its transitions. Each entry has its own `rememberSaveable` scope and `ViewModelStore`, released when the entry has left the stack and finished animating out. The phone layout's sidebar drawer (`CursorDrawer`) is built the same way: one value for how far open it is, moved by drags, programmatic open/close and the back gesture alike, so the gesture slides the sheet toward its edge in step with the finger — Material's `ModalNavigationDrawer` keeps its offset private and answers the gesture by shrinking the sheet toward whichever edge the swipe came from.
